### 2. 攻击路径验证

**调用链**：

✅ 调用链经代码逐级确认，完整可靠。

**报告遗漏的中间校验**：

报告未提及以下路径上的安全相关检查：

1. **`IPSEC_SOCKI_HandlePipeData` 的 a2 过滤**: `if ( !a2 || a2 == 2 )` — 只有a2为0或2时才继续处理，否则直接返回未初始化的result值。报告完全未提及此过滤。
2. **写管道拥塞检查**: `if ( *(_DWORD *)(v8 + 52) > 0x3FFu )` — 写队列深度>1023时拒绝读取。
3. **SOCK_RecvMbufEx_fl 返回值三重检查**: 
   - `v10 == -1 || !v95` → return 25
   - `v10 != -3840` → VRP_Assert + return
4. **VrId AVL3 查找**: `v11 = VOS_AVL3_Find(a4 + 276, &VrId, a4 + 300)` — 若VrId未找到，销毁数据包并返回7。
5. **ControlInfo分发逻辑**: `!ControlInfo` → Input路径; 有ControlInfo → Output路径。这意味着**入方向和出方向的选择依赖于MBUF元数据的ControlInfo标签(tag 10)，而非攻击者直接控制的字段**。
6. **ProtoType分发**: `ProtoType == 1` → IPv6, 否则 → IPv4。ProtoType同样来自MBUF元数据。

这些检查虽不是安全校验（它们是功能性路由逻辑），但说明从MBUF到Handle*Pkt之间的路径并非"无任何中间检查"。

**"10次重试"描述错误**：报告称`IPSEC_SOCKI_PipeData`有"10次重试"。实际代码：
```c
v8 = 10;
do {
    result = IPSEC_SOCK_ProcPipeData(...);
    if ( (_DWORD)result )   // 非零=错误 → break
      break;
    --v8;
} while ( v8 );
```
这是**在成功(result==0)时最多循环处理10个数据包**，遇到错误立即中断。不是"10次重试"(retry)，而是"10次连续处理"(batch)。语义完全不同。

### 3. 触发条件验证

报告声称"攻击者发送任何经过IPSec管道的网络数据包即可触达这些函数"——这是**过度简化**。实际触发需要满足：

1. 数据包必须通过`RTF_PipeMsgProcessFuncRegister`注册的管道到达`IPSEC_SOCKI_PipeMsg`。
2. `IPSEC_SOCKI_HandlePipeData`的a2参数必须为0或2。
3. `SOCK_RecvMbufEx_fl`必须成功返回-3840且v95非空。
4. VrId查找必须在AVL3树中找到对应条目。
5. 对应的IPSEC库实例`v14 = *(_QWORD *)(v11 + 40)`必须非空。

报告声称"数据包内容完全由攻击者控制"——**部分正确**。数据包payload（IP头、ESP/AH载荷）确实是攻击者可控的，但MBUF的ControlInfo(tag 10)和ProtoType等元数据是由网络协议栈设置的，不直接受攻击者控制。
