# 漏洞报告: IPSEC_SOCK_SendToSocket 中 SA 序列号递增操作 (*(_DWORD *)(a2 + 344) = v76/v77 + 1) 存在整数溢出

## 精确位置
- **函数名**: `IPSEC_SOCK_SendToSocket`
- **源文件**: `/home/qinghe/ai-workspace/target_libipsec/libipsec.so.c` (L40712-L41260)
- **漏洞代码行**: IPv4路径 `*(_DWORD *)(a2 + 344) = v76 + 1;` / IPv6路径 `*(_DWORD *)(a2 + 344) = v77 + 1;`
- **数据流关联**: INPUT-4 (a4) → v11 (VS节点) → a2=v15 (SA统计节点) → a2+344 (SA序列号)

## 漏洞类型与 CWE
CWE-190: Integer Overflow or Wraparound

## 严重性与置信度
严重性: Low
置信度: 低
**评级理由**: SA（Security Association）序列号 `*(a2+344)` 在每次数据包发送时递增。当序列号从 0xFFFFFFFF 递增到 0x00000000 时发生回绕。在 IPSec 协议中，序列号回绕可能导致安全问题（重放攻击窗口打开）。但这是 IPSec 协议本身的已知限制，通常通过 SA 重协商（rekeying）解决。

## 源代码片段
```c
// IPv4 路径:
      LODWORD(v76) = *(_DWORD *)(a2 + 344);     // 读取当前序列号
      *(_DWORD *)(a2 + 344) = v76 + 1;           // ← 序列号 + 1，无回绕检查
      v48 = IPSEC_SOCK_CopyDbgTracePacket(a4, a5, a3, &v62, &v63);

// IPv6 路径:
      LODWORD(v77) = *(_DWORD *)(a2 + 344);
      *(_DWORD *)(a2 + 344) = v77 + 1;           // ← 同样无回绕检查
      v52 = IPSEC_SOCK_CopyDbgTracePacket(a4, a5, a3, &v62, &v63);
```

## 完整攻击路径
1. **攻击入口**: 持续通过IPSec隧道发送大量数据包
2. **传播路径**:
   - 每个出方向数据包触发 `IPSEC_SOCK_SendToSocket`
   - 序列号 `*(a2+344)` 递增
   - 经过 2^32 个数据包后，序列号回绕到 0
3. **校验分析**: 
   - 没有序列号回绕检测
   - 没有触发 SA 重协商的逻辑
   - IPSec RFC 要求在序列号溢出前进行重协商
4. **触发点**: 序列号回绕后，新数据包的序列号与旧数据包重复

## 触发条件
- 发送超过 2^32（约43亿）个数据包通过同一个 SA
- 在高速网络（10Gbps+）上，小包情况下可能在数小时内达到
- 如果使用 ESN（Extended Sequence Number），则需要 2^64 个包，实际不可达

## 影响评估
- **重放攻击窗口**: 序列号回绕后，攻击者之前捕获的数据包的序列号变为"有效"，可以重放
- **IPSec RFC 合规性**: RFC 4303 要求在序列号即将溢出时通知密钥管理进行 SA 重协商
- **缓解因素**: 
  - IKE/IKEv2 密钥管理通常独立监控序列号并在接近溢出时触发重协商
  - 序列号溢出检测可能在 IPSEC_LIBI_HandleOutputPkt 中实现（本分析未跟入）
  - 实际触发需要极大量数据包传输
