# 漏洞报告: IPSEC_SOCKI_PipeMsg AVL3遍历中 a1 (PipeID) 直接赋值给 v7 导致管道ID伪造

## 精确位置
- **函数名**: `IPSEC_SOCKI_PipeMsg`
- **源文件**: `/home/qinghe/ai-workspace/target_libipsec/libipsec.so.c` (L44686-L44800)
- **漏洞代码行**: L44771 (`if (*v17 == a1) v7 = a1;`) 及 L44779 (`if (*v16 == a1) v7 = a1;`)
- **数据流关联**: INPUT-1 (a1, PipeID) → v7 → IPSEC_SOCKI_HandlePipeData 第5参数 (写管道ID)

## 漏洞类型与 CWE
CWE-20: Improper Input Validation

## 严重性与置信度
严重性: Medium
置信度: 中
**评级理由**: 当 `a2 == 0x3F0000` 且 a1 匹配 AVL3 树中某节点时，a1 被直接赋给 v7 作为"写管道ID"传递给后续处理函数。在其他路径中，v7 来自 a4 结构体的预配置字段（读管道ID对应的写管道ID），而此路径直接使用了外部输入 a1 作为写管道ID。这意味着攻击者控制的读管道ID可以被当作写管道ID使用，可能导致数据被发送到非预期的管道。

## 完整攻击路径
1. **攻击入口**: INPUT-1 (a1, PipeID) 和 INPUT-2 (a2, 消息类型)，通过RTF管道消息框架传入
2. **传播路径**:
   - 攻击者构造 a2 = 0x3F0000, a1 = 目标LDM树中已存在的管道ID
   - a1 不匹配主管道(a4+152)、PP4管道(a4+208)、LDM MB管道(a4+1296)
   - 进入 `a2 == 4128768` 分支，遍历 AVL3 树
   - 找到匹配节点后，`v7 = a1` — 读管道ID直接成为写管道ID
   - v7 传入 `IPSEC_SOCKI_HandlePipeData(a1, a3, a2, a4, v7)` 第5参数
   - → `IPSEC_SOCKI_PipeData` → `IPSEC_SOCK_ProcPipeData` → 入方向处理中作为 `a5` 参数
   - 在 `IPSEC_SOCK_SendToPP6orPP4orLDMPipe` 或 `IPSEC_SOCK_DbgTracePacket` 中被使用
3. **校验分析**: 
   - 其他路径中，写管道ID来自预配置的 a4 结构体字段（如 a4+140, a4+196, a4+1256, a4+8），这些由系统内部初始化
   - 本路径中 v7 = a1 是外部输入，绕过了"读管道→写管道"的映射关系
   - 但在 AVL3 树中的存在性检查（`*v17 == a1`）提供了部分验证
4. **触发点**: v7 作为写管道ID用于后续的 MBUF_Send_fl 调用

## 触发条件
- a2 必须等于 0x3F0000（特定消息类型）
- a1 必须匹配 LDM AVL3 树中某个节点的第一个 DWORD 字段
- a1 不得匹配主管道/PP4管道/LDM MB管道
- 读管道ID 被直接当作写管道ID使用

## 影响评估
- **管道混淆**: 攻击者可能使系统将处理结果发送到非预期的管道（使用读管道ID作为写管道ID），如果读写管道ID不同则会导致数据发送错误
- **DoS 可能**: 如果 v7 指定了不存在或无效的管道ID，后续 `MBUF_Send_fl` 可能失败
- **缓解因素**: AVL3 树中的存在性检查限制了 a1 必须是已注册的合法管道ID；`IPSEC_SOCK_SendToPP6orPP4orLDMPipe` 内部有管道ID有效性检查（`v10 == -1`）和管道状态检查（opened状态）
- **设计意图分析**: 此处可能是有意设计，在 LDM 树匹配时使用同一个管道ID 作为双向标识。如果读写管道是同一个 pipe 实例，则没有安全问题。需要更多上下文确认。
