# 第一步：建立攻击面地图（基于数据流分析）

阅读上述任务中指定的**数据流分析文件**（必须完整阅读，一字不漏），提取：

1. **目标函数**：函数名、签名、功能、在系统中的角色
2. **攻击面清单**：所有 INPUT-N 标记的外部输入——这些就是攻击者的"弹药入口"
3. **污点传播图谱**：每个 INPUT 的数据流树，关注每一个分叉和派生值
4. **高价值攻击点**：
   - `🟡 EXPORT` 终点 — 数据进入外部函数，**必须跟入源码检查目标函数对数据的处理是否安全**
   - `📌 USED` 终点 — 数据被用于操作，**必须检查该操作是否存在漏洞**
   - `🟢 CLEANED` 终点 — **必须验证清洗逻辑是否真正有效，能否绕过**
   - `[DEFERRED]` 终点 — 数据被存储，需评估后续使用风险
5. **数据流标注的关键发现**：★ 标记的问题
6. **子追踪**：被调用函数的内部数据流

# 第二步：源码深度审计（核心工作）

打开任务中指定的**源码目录**中的文件，逐函数、逐行审计。

## 2.1 验证并扩展数据流分析

- 验证数据流分析的每条路径在源码中的真实行为
- **主动寻找数据流分析遗漏的路径**：
  - 错误处理分支
  - 条件编译/宏展开后的隐藏逻辑
  - 回调/函数指针间接调用
  - 循环内的累积效应
  - 多线程/中断上下文的交互

## 2.2 对每个 EXPORT 终点进行安全审计

这是**最关键的分析步骤**——数据流分析只告诉你"数据传入了 func_X"，你必须：

1. 在源码中找到 func_X 的实现
2. 追踪传入的数据在 func_X 内如何被使用
3. 用完整的漏洞检查清单（见 system prompt）扫描 func_X
4. 如果 func_X 又调用更深的函数，继续跟踪（至少 3 层深度）

## 2.3 对每个 USED 终点进行漏洞模式扫描

对每个数据消费点，用你的漏洞检查清单逐项扫描：

- 作为**长度参数**：可能导致缓冲区溢出
- 作为**数组索引**：可能导致越界读写
- 作为**指针运算操作数**：可能导致任意地址访问
- 作为**比较对象**：可能导致逻辑绕过
- 作为**循环边界**：可能导致无限循环或越界
- 作为**分配大小**：可能导致整数溢出后的小缓冲区分配
- 作为**类型转换输入**：可能导致符号混淆或截断

## 2.4 对每个 CLEANED 终点进行绕过分析

数据流标记了 `🟢 CLEANED` 不代表真的安全：

- 校验条件是否完备？（`<` vs `<=`，off-by-one）
- 有符号/无符号比较是否正确？
- 是否有整数溢出导致校验失效？
- 校验和使用之间是否有 TOCTOU 窗口？
- 是否只校验了部分字段？

## 2.5 超越数据流的全局扫描

数据流分析是按 INPUT 维度组织的，你还需要：

- 检查函数中**未被数据流覆盖的代码区域**
- 查找**硬编码凭据、不安全的默认配置**
- 检查**错误处理路径**是否安全
- 检查**调用者上下文**，确认外部输入确实可达

# 第三步：撰写漏洞报告

对每个发现的漏洞（无论置信度），在 `results/` 目录下创建 `result_NNN.md`：

```markdown
# 漏洞报告: [一句话描述漏洞本质]

## 精确位置
- **函数名**: [完整函数名]
- **源文件**: [文件路径]
- **漏洞代码行**: [具体行号]
- **数据流关联**: [对应 INPUT-N / 路径 / 终点类型]

## 漏洞类型与 CWE
[CWE-XXX: 具体分类]

## 严重性与置信度
严重性: Critical / High / Medium / Low
置信度: 高 / 中 / 低
[评级理由]

## 源代码片段
​```c
[漏洞相关代码，不少于 5 行上下文]
​```

## 完整攻击路径
1. **攻击入口**: [INPUT-N, 攻击者如何控制]
2. **传播路径**: [数据如何从入口流到漏洞点，列出每一步]
3. **校验分析**: [路径上有哪些校验？为什么不够？如何绕过？引用代码]
4. **触发点**: [最终触发什么危险操作]

## 触发条件
[具体到字段、取值范围、前置条件。攻击者需要构造什么样的输入？]

## 影响评估
[漏洞后果：RCE / 任意内存读写 / 信息泄露 / DoS / 权限提升？影响范围？]
[是否考虑了 ASLR/DEP/Canary 等缓解措施？]
```

**质量要求**：
- 每个漏洞**必须**有源代码片段
- 每个漏洞**必须**有从 INPUT 到危险操作的完整路径
- 不确定的发现也要报告，标注置信度为"低"
- 禁止模板化复制——每个报告必须有独立分析

# 第四步：撰写总结报告

在工作目录创建 `summary.md`，**必须包含以下全部章节**：

### 1. 攻击面分析
- 目标函数的角色、外部输入来源
- 攻击者能力模型：哪些输入可控、控制程度如何

### 2. 分析方法与覆盖度
- 你的分析策略
- 数据流路径覆盖度

| 路径 | 起点 → 终点 | 终点类型 | 深度分析 | 漏洞模式扫描 | 结论 |
|------|-------------|---------|---------|-------------|------|
| INPUT-1 → func_A | ... | EXPORT | ✅/❌ | ✅/❌ | 安全/漏洞 |

### 3. EXPORT 终点跟入分析汇总
- 每个 EXPORT 终点是否跟入了目标函数
- 跟入后发现了什么

### 4. 漏洞发现汇总表

| 编号 | 报告文件 | 函数 | CWE | 严重性 | 置信度 | 摘要 |
|------|---------|------|-----|--------|--------|------|

### 5. 关键发现验证
- 数据流 ★ 标记的关键发现验证结论

### 6. 总体风险评估
- 整体安全风险
- 修复优先级建议

### 7. 局限性
- 未跟入的 EXPORT 函数
- 未完整追踪的路径
- 需要额外分析的方向
