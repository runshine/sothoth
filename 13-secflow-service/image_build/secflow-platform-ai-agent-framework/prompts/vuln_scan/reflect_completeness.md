## 一、数据流覆盖度反思

1. **路径完整性**：回顾数据流分析文件中的所有 INPUT 和派生值。每个 INPUT 的传播树中，是否所有分支你都已追踪？是否有某些分支被你忽略？
2. **EXPORT 终点覆盖**：数据流分析中标记为 🟡 EXPORT 的终点，你是否都尝试跟入了目标函数的源码？如果有未跟入的，列出并说明原因。
3. **USED 终点覆盖**：数据流分析中标记为 📌 USED 的终点，你是否都检查了操作的安全性？是否有遗漏的 USED 终点？
4. **DEFERRED 终点处理**：标记为 [DEFERRED] 的数据，你是否评估了它们被后续使用时的安全风险？
5. **关键发现验证**：数据流分析中 ★ 标记的关键发现，你是否**全部**做了源码级验证？

## 二、分析深度反思

6. **源码验证**：你的分析是基于**实际阅读源代码**，还是仅仅复述了数据流分析的内容？每个结论是否有源代码行级证据支撑？
7. **跨函数追踪**：当污点数据传入被调用函数时，你是否追踪到了该函数内部的处理逻辑？还是仅在函数边界停止？
8. **校验评估**：对于存在安全校验的路径，你是否分析了校验的充分性？仅存在校验不等于路径安全——校验可能不完整或可绕过。
9. **边界条件**：你是否考虑了边界情况——如整数最大值/最小值、空字符串、零长度缓冲区、NULL 指针等特殊输入？

## 三、报告质量反思

10. **代码证据**：每个漏洞报告是否都引用了实际的源代码片段（≥5 行上下文）？是否有报告缺少代码证据？
11. **数据流闭合**：每个漏洞的攻击路径是否从数据流分析的 INPUT 出发、经过中间处理、最终到达危险操作？链条中是否有未验证的跳跃？
12. **触发条件具体性**：每个漏洞的触发条件是否具体到字段和取值范围？能否据此构造实际的测试输入？
13. **影响评估合理性**：严重性评级是否与实际影响匹配？是否存在过度夸大或过度保守的评估？

## 四、误报排查

14. **可达性验证**：对于你报告的每个漏洞，外部输入是否真的能到达漏洞点？是否存在上游调用者已经做了充分过滤的情况？
15. **反编译/宏展开假象**：如果分析涉及宏定义或条件编译，你是否考虑了不同编译配置下代码的实际行为？
16. **多余报告**：是否存在两个报告实际描述同一个漏洞（从不同路径到达同一缺陷点）的情况？如有，应合并。
