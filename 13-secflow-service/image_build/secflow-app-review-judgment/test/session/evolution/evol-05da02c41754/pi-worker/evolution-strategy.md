# 漏洞挖掘执行策略

## 本轮任务背景

已有 13 个 CONFIRMED 漏洞，覆盖 ESP/AH 输入处理、IPv4/IPv6 双版本、packet_info 偏移写、整数截断、Pipe ID 等多个维度。当前数据流分析存在 303 个 DIRECT_SINK，是主要候选池。

## 优先追的路径

**沿用已有模式扩相邻路径**
- 已有整数截断导致 Pipe ID 冲突 → 检查同类位置是否还有截断（32→16 位出现多次）
- 已有 AH/ESP 中 packet_info[1] 被污染 → 排查同结构体中其他 field 是否同样被污染
- 已有 ESP 输出路径中 Header Length 做 malloc size → 搜索同类 malloc/alloc 调用，污染来自哪一层

**双版本对照补漏**
- IPv4 和 IPv6 版本存在对应函数（如 IPSEC_AH_HandleInputPkt V4 vs 非 V4），已有结果若只覆盖单版本，对侧必须补查
- IPv6 扩展头解析已有偏移溢出 → 同样逻辑若出现在 IPv4 的 IP Options 解析中，要对比验证

**危险函数族重点排查**
- 整数运算后进入 memcpy/memmove/strcpy/sprintf 的位置
- 指针算术后直接解引用（packet_info[1] 模式）
- 分配大小受污染字段控制的位置

## 遇到以下情况应该补证据或扩路径

- 发现疑似漏洞但数据流只到 USED 而非 DIRECT_SINK → 继续追污点是否继续传播
- 同一函数内存在 CLEANED 标记 → 必须核实清洗是否真正支配了危险操作，否则按漏洞论
- 函数边界存在 EXPORT 标记 → 追出去找到接收函数，看是否继续形成危险
- 已有结果中的前置条件（如"需要特定 SPI 值"）→ 要在源码中核实该条件是否真实可控

## 禁止行为

- 不许把"理论可能"写成漏洞，必须有源码级证据
- 不许跳过数据流闭环验证
- 不许在没有核实边界条件的情况下声称"可达"
