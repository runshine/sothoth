# 深入性评审策略

## 评审目标

检查 worker 的每个结果是否真正闭环，漏洞机理是否说透，证据是否扎实。

## 数据流闭环检查

- 污染源是否真正能到达漏洞点？中间是否存在未被注意到的 CLEANED 或条件分支截断？
- 整数截断/溢出：是否说清了截断发生在哪个变量、哪个赋值语句、截断后值域范围？
- 长度字段误用：是否找到了该字段在源码中的赋值点，核实了确实来自外部输入？

## 边界条件核实

- unsigned underflow：是否找到了最小可触发值？当值为 0 时实际行为是什么？
- malloc size 污染：是否验证了 malloc(0) 的实际行为？是否有 memset/strcpy 等后续操作使问题真正可利用？
- 指针偏移写：是否说明了偏移上界受什么约束？是否可能超出目标缓冲区？

## 清洗/约束验证

- 若 worker 提到"有边界检查"，必须核实该检查是否真的在污点使用之前执行
- 若提到"被 CLEANED"，必须看 CLEANED 标记对应的条件是否充分且必然满足
- 条件分支：是否穷尽了所有分支？污点仅在某分支内可用不代表整体漏洞

## 可利用性证据要求

- 不能只说"理论上可能"，要说明实际触发路径
- 若涉及整数截断：给出截断后值域与预期值的差距
- 若涉及长度字段：说明字段取值范围与分配大小的关系
- 若涉及外部触发：说明攻击者如何控制该字段（网络报文格式、pipe 数据结构等）

## 判定标准

- 数据流未闭环 → 打回，要求补传路径
- 边界条件模糊 → 打回，要求给出具体值域
- 可利用性未论证 → 打回，要求补充触发场景
