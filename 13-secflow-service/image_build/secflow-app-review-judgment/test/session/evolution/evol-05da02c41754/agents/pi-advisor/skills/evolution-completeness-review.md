# 全面性评审策略

## 评审目标

检查 worker 是否覆盖了所有应查路径，是否遗漏了与已有漏洞相邻的可疑点。

## 覆盖完整性核查

**数据流层面**
- 303 个 DIRECT_SINK 是否全部被过筛？还是 worker 只挑了部分？
- 74 个 USED 中是否存在应该继续追但被截断的路径？
- 31 个 EXPORT 是否有应该追出去但没追的？

**函数层面**
- 61 个跟踪函数中，是否有函数完全没有被覆盖（即使有污点标记）？
- 同族函数（如 AH/ESP、V4/non-V4）的双版本是否都查了？

## 遗漏模式检查

以下模式若存在必须补：
- **同源同sink**：同一污染源（A）到达多个同类 sink（B1/B2/B3），已查 B1 但漏了 B2
- **跨函数传播断链**：污点从 A→B→C，但 B→C 段没有闭环验证
- **版本缺失**：IPv4 版本有漏洞，但 IPv6 版本对应逻辑没有查
- **结构体成员漏查**：packet_info[1] 有漏洞，同结构体其他成员是否也可能被污染？

## 与已有结果相邻路径检查

- 已有整数截断漏洞 → 搜索同函数/同文件是否还有其他截断点
- 已有 Header Length 做 malloc size → 搜索其他字段是否也用于分配大小
- 已有 Packet Info 偏移写 → 检查其他函数中是否存在类似的 packet_info 用法

## 判定标准

- 若有 DIRECT_SINK 从未被 worker 提及，必须打回
- 若同模式漏洞只报了一个但明显存在多个，必须指出遗漏位置
- 若 EXPORT 路径未追且可能形成漏洞，必须要求补充
