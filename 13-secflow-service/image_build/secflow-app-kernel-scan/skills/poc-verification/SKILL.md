# PoC 验证

## 概述

根据现有漏洞报告提取触发条件，编写最小可复现 PoC，完成交叉编译、推送到设备模拟器、直接用root权限执行验证和报错修复，多轮运行直到漏洞触发，验证是否为漏洞以触发手机panic为准。

优先输出能真正落地的验证结果，不停留在“可能可利用”的分析层面。


## 判断漏洞真实存在原则
- 运行POC时需要同时运行dmesg监控手机内核日志看是否崩溃。
- 如果是条件竞争漏洞、uaf、double free， 越界写等内存破坏类漏洞：需要写poc触发手机panic，如果能二次稳定panic，才能认定为漏洞。
- 如果是越界读，整数溢出等泄漏类漏洞，需要成功读写出有意义的内核数据（比如内核地址）到用户态才能说明漏洞真实存在，否则不能说明漏洞真实存在。
```bash
# 比如copy_from_user时越界读了内核数据，但是dmesg显示失败了，说明不能越界读。
```
- 只要触发了手机panic，说明漏洞是真实存在的。

## 工作流程


### 1. 先读报告，确定攻击入口

优先从报告中确认以下信息：

- 漏洞类型
- 触发入口：`ioctl`、`write`、`read`、`mmap`、`setsockopt`、`netlink`、`procfs`、`sysfs`, `syscall`
- 用户态可控字段
- 目标节点、设备文件、系统调用或协议族
- 成功判据：崩溃、内核日志、返回值异常、卡死、内存破坏迹象

如果报告没有写清这些内容，先补齐：

- 攻击路径
- 受影响函数
- 用户态输入如何流入危险点


### 2. 确定要使用的设备和工具
根据用户的要求，只加载对应设备的工具使用方法：
- 如果要求在华为设备上测试则使用hdc，参考：`references/huawei_device_hdc_usage.md`
- 如果要求在安卓设备上测试则使用adb，参考：`references/android_device_adb_usage.md`

### 3. 检查特性是否开启

- 根据源码或者报告中的描述，确认目标设备的内核配置是否开启了相关特性（比如：CONFIG_HUAWEI_SOMETHING），如果没有开启，说明该漏洞在目标设备上无法触发。
- 写个简单的poc验证特性是否开启。
- 如果需要的特性全部开启则继续poc验证漏洞。

### 4. 从报告抽取 PoC 输入

优先使用 `scripts/extract_report_info.py` 从 Markdown 报告提取结构化信息：

```bash
python3 scripts/extract_report_info.py /path/to/report.md
```

该脚本会抽取：

- 漏洞标题
- 类型
- 严重程度
- 位置
- 描述
- 利用场景
- 攻击路径
- 参考编号

如果脚本没能提取完整信息，再手动补齐。

### 5. 编写 PoC

PoC 默认使用 C 语言，遵守以下原则：
- poc 尽可能触发panic，方便确认漏洞是否真实存在
- 先写最小触发器，只保留与漏洞相关的参数
- 区分“验证触达路径”和“验证真正内存破坏”

PoC 至少应包含：
- 设备是否panic
- 参数校验
- 清晰的日志输出
- 成功与失败返回码
- 必要的 `open`/`ioctl`/`write`/`mmap`/`socket` 调用
- 触发后等待或重复触发逻辑（如果竞态或异步路径需要）

如果报告来自内核源码扫描，PoC 里要把用户态可控字段与报告中的危险变量一一对应。

### 6. 编译
根据设备类型选择对应的编译工具，详情参考对应设备的reference

修复编译错误时按下面顺序处理：

- 缺少头文件：补标准头或内核 UAPI 头
- 结构体不匹配：改用报告对应版本的字段布局
- 宏缺失：补本地定义，但要注明来源
- 32/64 位不匹配：显式使用 `uint32_t`、`uint64_t`、`uintptr_t`
- 对齐问题：使用 `__attribute__((packed))` 时要谨慎，只在协议/IOCTL 布局明确时使用

不要为了“编过”而随意删掉关键字段。

### 7. 运行和设备状态检测
- 直接使用su运行poc。
- 运行过程中实时通过dmesg监控poc的内核日志，同时看内核是否panic。
- 如果检测到设备重启，需要重新推送poc到手机上运行进行二次验证。

## 输出要求
- 说明是否触发，设备是否panic。
- PoC 文件统一放到当前工作区的 `./AI4EXP` 中，再推送到手机。
执行该技能时，最终产物应尽量包含：

- `./AI4EXP/*.c` PoC 源码
- `./AI4EXP/` 下的可执行文件
- 运行命令
- 关键报错与修复说明
- 最终验证结论

若同时需要报告，可补充一段简洁中文结论：

- 是否成功触发
- 触发使用的接口
- 非 `root` 是否可达
- 是否观测到崩溃、异常返回、日志告警或其他可验证现象
- 若失败，失败在什么环节
