# 系统分析微服务（secflow-app-system-analyse）架构设计文档

> **版本**: v2.0 | **日期**: 2026-06-12 | **密级**: 内部

---

## 一、服务定位

**一句话描述**：该系统分析服务是一个"AI 安全分析师"，能够自动对解包后的固件或软件包进行**功能模块划分**，然后对每个模块执行 **STRIDE 安全威胁分析**，最终自动生成一份专业的**安全分析总报告**。

**核心价值**：
- 替代人工逐文件审查，将数小时的安全分析工作缩短为数十分钟
- AI 驱动的威胁建模，覆盖 6 大安全维度（身份伪造、数据篡改、抵赖、信息泄露、拒绝服务、权限提升）
- 自动化输出结构化的安全报告，可直接用于安全评审

## 三、分析流水线（四阶段 14 步骤）

整个分析过程分为 **四个大阶段**，共 **14 个步骤**，从前到后串行执行：

```
【阶段 0：预处理】→【阶段 1：功能模块划分】→【阶段 2：模块细分】→【阶段 3：安全分析】→【阶段 4：生成报告】
```

### 3.1 阶段 0：智能预处理（7 个步骤，纯工具执行）

> **目标**：看懂待分析的软件包里都有什么文件，做好分类和索引，为后续 AI 分析做好准备。

| 步骤 | 名称 | 作用 | 通俗理解 |
|------|------|------|---------|
| S0.1 | 文件过滤 | 根据用户要求筛选需要分析的文件（如只看 ARM 平台的二进制） | "从仓库里挑出要检查的货物" |
| S0.2 | 文件类型识别 | 识别每个文件的类型（二进制/源码/脚本/配置等） | "给每件货物贴标签" |
| S0.3 | 未知文件识别 | 对无法自动识别的文件，调用 AI 辅助判断 | "看不清楚的让 AI 帮忙认" |
| S0.4 | 目录结构探索 | AI 扫描目录结构，提取功能关键词 | "通过文件名推断软件有哪些功能" |
| S0.5 | 关键词预扫描 | 用脚本统计高频关键词，按功能分组 | "统计词频，自动归类" |
| S0.6 | 路径先验分组 | 根据目录层级推断模块边界 | "从目录结构猜功能模块" |
| S0.7 | 全量文件预读 | 对每个文件提取关键信息（符号表、函数名、导入依赖） | "给每件货物生成档案卡" |

**本阶段不消耗 AI Token，完全由脚本和工具完成。**

#### 阶段 0 核心产物：

```
workspace/
├── filtered_files.txt      # 待分析文件清单（如：1157 个文件）
├── file_catalog.json       # 文件类型目录（每个文件是什么类型）
├── details/
│   ├── path/to/file1.json  # 文件1的档案卡（符号表、函数名、依赖等）
│   ├── path/to/file2.json  # 文件2的档案卡
│   └── ...                 # 每个文件一个
├── keywords.txt            # 功能关键词
├── keyword_summary.txt     # 关键词统计摘要
└── classify_context.md     # 分类上下文（按类型分组的文件汇总）
```

### 3.2 阶段 1：功能模块粗分类（AI Worker + AI Judge 循环）

> **目标**：把分散的文件按照功能归属，划分成若干个"功能模块"。

**核心机制：Worker（工人）+ Judge（评审）多轮循环**

```
┌──────────────────────────────────────────────────────────┐
│                    W+J 多轮评审循环                       │
│                                                          │
│   ┌──────────┐          ┌──────────┐                    │
│   │  Worker  │ ──────→  │  Judge   │                    │
│   │ (AI工人) │  输出结果  │ (AI评审) │                    │
│   └──────────┘          └────┬─────┘                    │
│        ↑                     │                          │
│        │         评审不通过    │  评审通过                │
│        │     (反馈修改意见)   │  且达到最少轮数           │
│        └─────────────────────┼─────────→ 进入下一阶段    │
│                              │                          │
│   最多重试轮数由配置控制（默认无上限）                    │
└──────────────────────────────────────────────────────────┘
```

**Worker 的工作**：
- 读取每个文件的"档案卡"（details/ JSON）
- 判断哪些文件属于同一个功能模块
- 创建模块目录，将文件路径写入 `files.list`

**Judge 的评审标准**：
- **零遗漏铁律**：所有文件都必须被分配到一个模块中，遗漏一个就判不通过
- 模块划分是否合理（不能把无关文件放在一起）

#### 阶段 1 核心产物：

```
workspace/modules/
├── network/
│   └── files.list          # 网络相关文件列表
├── crypto/
│   └── files.list          # 加密相关文件列表
├── ipc/
│   └── files.list          # 进程间通信相关文件列表
└── ...                     # 多个功能模块
```

### 3.3 阶段 1.5：安全维度过滤（可选）

> **目标**：如果用户只关心特定安全问题（如"网络协议"和"认证授权"），则自动剔除无关模块。

- Worker 逐模块判断是否与指定安全维度相关，无关的直接删除
- Judge 检查删除是否正确，输出"需恢复/需删除"列表
- 支持的安全维度包括：网络协议解析、文件格式处理、认证与访问控制、密码学操作、进程间通信、配置解析、输入验证、权限管理、Web API、内存管理等 10 个维度。

### 3.4 阶段 2：模块细分（多模块并行 + AI 循环）

> **目标**：对每个功能模块，判断是否需要进一步拆分或合并，使每个模块职责单一。

**核心设计：并行处理 + 串行提交**

```
                     待处理模块队列
                     ┌─────────────┐
                     │ crypto      │
                     │ network     │
                     │ ipc         │
                     │ ...         │
                     └──────┬──────┘
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ┌────────────┐    ┌────────────┐    ┌────────────┐
   │ AI线程 #1  │    │ AI线程 #2  │    │ AI线程 #3  │
   │ 处理crypto │    │ 处理network│    │ 处理ipc    │
   │ W+J 循环   │    │ W+J 循环   │    │ W+J 循环   │
   │            │    │            │    │            │
   │拆分决策:    │    │拆分决策:    │    │拆分决策:    │
   │crypto→     │    │network→    │    │ipc→        │
   │ crypto_aes │    │ network_tcp│    │ (不拆)     │
   │ crypto_rsa │    │ network_udp│    │            │
   └─────┬──────┘    └──────┬──────┘    └──────┬──────┘
         │                  │                  │
         └──────────────────┼──────────────────┘
                            ▼
              ┌─────────────────────────┐
              │   串行提交线程          │
              │   • 校验拆分完整性       │
              │   • 执行模块创建/合并    │
              │   • 新子模块重新入队     │
              └─────────────────────────┘
```

**三种拆分模式**：

| 模式 | 操作 | 示例 |
|------|------|------|
| 全拆分 | 原模块完全拆成多个独立子模块 | `ssh` → `ssh_server` + `ssh_client` |
| 部分拆分 | 原模块保留部分文件，拆出独立子模块 | `crypto` → `crypto` + `crypto_pki` |
| 合并 | 部分文件合并到已存在的其他模块 | `utils` 中的文件 → 合并到各自功能模块 |

**并行设计说明**：
- 配置 `parallel_modules=N` 控制同时处理的模块数，默认 1（串行）
- 每个模块独立进行 W+J 多轮循环，互不干扰
- "串行提交线程"确保模块拆分/合并时不会出现文件归属冲突
- 所有模块处理完毕后，执行一次全局检查，确保没有文件遗漏

#### 阶段 2 核心产物：

```
workspace/modules/               # 细分后的模块（可能比 S1 更多）
├── ssh/
│   └── files.list               # SSH 客户端+服务端（合并为一个模块）
├── crypto_aes/
│   └── files.list               # AES 加密实现
├── crypto_rsa/
│   └── files.list               # RSA 加密实现
├── tls/
│   └── files.list               # TLS 协议实现
└── ...
```

### 3.5 阶段 3：安全威胁分析（多模块并行 STRIDE 分析）

> **目标**：对每个模块执行 STRIDE 安全威胁建模，生成结构化的安全分析报告。

**STRIDE 威胁模型**（业界标准安全分析方法）：

| 威胁类型 | 含义 | 通俗理解 |
|---------|------|---------|
| **S**poofing | 身份伪造 | 有人冒充合法用户/服务 |
| **T**ampering | 数据篡改 | 数据在传输/存储中被修改 |
| **R**epudiation | 抵赖 | 用户否认做过某个操作 |
| **I**nfo Disclosure | 信息泄露 | 敏感数据被未授权访问 |
| **D**oS | 拒绝服务 | 攻击导致服务不可用 |
| **E**levation | 权限提升 | 普通用户获取管理员权限 |

**Worker 的分析过程**：
1. 读取模块中每个文件的"档案卡"（符号表、函数名、依赖）
2. 从 6 个维度逐一分析可能的安全风险
3. 给出风险等级（高/中/低）和风险评分（0-100 分）
4. 直接写入 `module_report.md`（使用 AI 的写作能力）

**Judge 的评审标准**：
- 每个 STRIDE 维度是否都有覆盖
- 风险等级的判定是否合理
- 分析深度是否足够（不能草草了事）

**并行执行**：多个模块的分析同时进行，每个模块独立 W+J 循环，互不干扰。

#### 阶段 3 核心产物（每个模块一份）：

```
workspace/modules/ssh/module_report.md
```

**报告内容示例**：
```markdown
# SSH 模块安全分析报告

## 基本信息
- 风险等级：高
- 风险评分：75

## STRIDE 威胁分析

### 🔴 身份伪造 (Spoofing)
- 风险点：SSH 握手阶段未正确验证服务器证书
- 影响：中间人攻击可能导致凭据泄露
- 修复建议：启用严格的证书链校验

### 🟡 数据篡改 (Tampering)
- 风险点：...（省略）
...

## 暴露面分析
- 网络端口：22 (SSH)
- 依赖库：libssl-1.1.so, libcrypto-1.1.so

## 修复建议
1. [高] 启用证书链校验...
2. [中] 限制加密算法白名单...
```

### 3.6 阶段 4：生成最终报告（2 个步骤）

> **目标**：把所有模块的分析整合成一份总报告，完成最终交付。

| 步骤 | 名称 | 作用 |
|------|------|------|
| S4a | 完整性检查 | 确保每个模块都有分析报告，缺失的模块触发 S2+S3 补做 |
| S4b | 报告生成 | 程序化汇总所有模块报告，按风险排序，生成总报告 |

**最终交付物**：

```

```

## 四、AI 智能体运行机制

### 4.1 双层容错设计

```
┌─────────────────────────────────────────────┐
│              第一层：API 调用级重试           │
│  • 网络超时、服务器繁忙 → 自动等待重试       │
│  • 重试间隔：3秒 → 5秒 → 10秒 → 15秒 → 30秒  │
│  • 最多重试 5 次（可配置）                   │
├─────────────────────────────────────────────┤
│              第二层：进程级重试               │
│  • AI 进程崩溃/被系统杀死 → 重新启动          │
│  • 自动继承之前的对话上下文（不丢失进度）      │
│  • 最多重试无限次（可配置）                   │
└─────────────────────────────────────────────┘
```

### 4.2 AI"卡死"自动恢复

当 AI 模型超过 30 分钟没有响应时：
1. 系统检测到卡死 → 发送"请继续"激活指令
2. 如果仍然无响应 → 重启 AI 进程，保留历史对话
3. 最多激活 5 次（可配置），超过则自动重启

### 4.3 对话上下文管理

- AI 分析过程产生大量中间对话，会占用模型处理能力
- 系统自动压缩历史对话，保留关键结论、丢弃冗余细节
- 保留 50000 个最近 Token 的对话内容供 AI 参考

## 八、关键技术指标

| 指标 | 说明 |
|------|------|
| **分析效率** | 一个典型嵌入式固件（~1000 文件）的分析时间从人工数小时缩短到数十分钟 |

| **模型灵活切换** | 支持 GLM-5 / MiniMax / GPT-5.4 等多种大模型，通过配置中心动态切换 |
| **并行处理** | 多模块并行分析，并行度可通过 `parallel_modules` 配置 |

## 十、总结

本系统分析服务通过 **"工具预处理 + AI 智能分析 + 专家评审循环"** 的三层架构，实现了从固件/软件包到安全分析报告的端到端自动化流程。其核心创新点包括：

1. **W+J 多轮评审循环**：Worker 产出 + Judge 评审 + 反馈改进，确保输出质量
2. **并行 LLM + 串行提交**：在保障数据一致性的前提下最大化 AI 处理吞吐量
3. **双层容错 + 卡死恢复**：确保长时间运行的任务稳定可靠
4. **断点续跑**：14 个检查点支持任意阶段的恢复，避免重复计算
5. **可配置的安全维度**：10 个安全维度按需选择，适配不同业务场景
