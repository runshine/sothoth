# Review-Driven Multi-Agent Vulnerability Discovery

设计一套基于评审反馈的多轮次多 Agent 漏洞挖掘系统。系统输入为一个模块的代码与从模块入口函数开始的数据流/污点分析文件；核心目标是在控制误报与资源成本的前提下，通过“全面性评审”和“深入性评审”持续降低漏报，发现更全面、更深层、更容易被忽略的复杂漏洞模式。

## Context
- 本计划未读取任何仓库文件，遵循用户“不要阅读任何文件，根据需求独立思考”的要求。
- 目标系统不是简单让多个 LLM 重复审计，而是引入可度量的覆盖模型、探索状态、证据质量、边际收益与停止准则。
- 系统包含：
  - 漏洞挖掘 Agent / Worker：负责按任务卡执行漏洞发现、补充证据、产出候选漏洞。
  - 全面性评审 Agent：负责判断“还有哪些区域/入口/数据流/威胁类型没有覆盖”，输出下一轮广度探索方向。
  - 深入性评审 Agent：负责判断“当前分析是否停留在浅层模式”，输出复杂路径、跨函数、状态机、时序、隐式约束、组合漏洞等深挖方向。
  - 结果误报评审 Agent：负责验证新增漏洞，维护漏洞结果列表状态：待结果评审、确认是漏洞、确认为误报。
  - Orchestrator / 调度器：程序化控制轮次、预算、状态机、停止条件、任务分配和上下文压缩；LLM 只能给停止建议，最终停止由程序控制。

## Plan:
1. 定义统一的系统状态模型。
   - 维护 `AuditState`：模块元信息、入口函数、代码摘要、污点图摘要、调用图、数据流路径、资产/安全边界、已审计区域、未审计区域、候选漏洞列表、确认漏洞列表、误报列表、每轮任务与反馈。
   - 维护 `ExplorationLedger`：用于防止多轮空转，记录每个探索方向是否已尝试、尝试结果、新增发现、失败原因、是否可继续拆解。
   - 维护 `CoverageMatrix`：以入口、source、sink、路径、函数、权限边界、状态转换、漏洞类别、攻击面为维度衡量覆盖。
   - 维护 `DepthMatrix`：以路径长度、跨函数/跨文件、别名/指针/对象生命周期、条件约束、状态依赖、并发/时序、二次传播、组合利用链等维度衡量深度。

2. 将 Worker 从“自由审计”改造成“执行任务卡”的 Agent。
   - Worker 每轮必须接收明确的 `TaskCard`，包括：本轮目标、范围、禁止重复区域、重点数据流、待验证假设、期望输出、证据标准。
   - Worker 输出必须结构化：新增候选漏洞、路径证据、source 到 sink 链路、触发条件、消毒/校验绕过点、影响、利用前置条件、不确定性、下一步建议。
   - Worker 不直接决定结束，只能报告“本轮无新增发现”和原因。

3. 设计全面性评审 Agent 的评判职责。
   - 核心问题：当前漏洞挖掘是否覆盖了所有合理攻击面、数据流路径、漏洞类型和边界场景？
   - 评判维度：
     1. 入口覆盖：模块入口函数、回调、RPC/API handler、CLI 参数、配置加载、消息队列、文件/网络输入是否覆盖。
     2. Source 覆盖：用户输入、配置、环境变量、数据库、缓存、外部服务返回、反序列化对象、文件内容、跨模块参数是否覆盖。
     3. Sink 覆盖：命令执行、SQL/NoSQL 查询、文件路径、模板渲染、反序列化、内存操作、鉴权决策、权限变更、加密/签名、网络请求、日志/审计、资源分配是否覆盖。
     4. 路径覆盖：污点图中高风险路径、未检查路径、分叉路径、异常路径、默认分支、错误处理路径、早返回路径是否分析。
     5. 漏洞类别覆盖：注入、越权、认证绕过、路径遍历、SSRF、反序列化、XSS/模板注入、信息泄露、竞态、DoS、逻辑漏洞、加密误用、内存安全等是否覆盖。
     6. 安全边界覆盖：用户/管理员、租户、命名空间、进程边界、容器边界、内外网边界、可信/不可信数据边界是否覆盖。
   - 输出不是泛泛建议，而是按优先级给出“覆盖缺口任务卡”：例如“污点路径 P12/P13 到 file_open sink 未被审计；优先检查路径规范化、符号链接、TOCTOU”。

4. 设计全面性评审 Agent 的量化评分。
   - `attack_surface_coverage`：已覆盖入口/攻击面比例。
   - `source_sink_coverage`：已覆盖 source-sink 对比例，按风险权重加权。
   - `vuln_class_coverage`：高相关漏洞类别覆盖程度。
   - `path_coverage`：污点路径覆盖程度，区分完整审计、粗略扫过、未审计。
   - `boundary_coverage`：安全边界和权限模型覆盖程度。
   - `novelty_score`：下一轮建议与历史任务的差异度，防止重复。
   - 全面性评审必须输出：覆盖热力图、Top-N 缺口、每个缺口的风险理由、建议任务卡、预期能发现的漏洞类型。

5. 设计深入性评审 Agent 的评判职责。
   - 核心问题：Worker 当前是否只做了表层模式匹配，而没有深入证明复杂漏洞？
   - 评判维度：
     1. 路径深度：是否跨多函数、多文件、多对象、多异步阶段追踪 source 到 sink。
     2. 条件约束深度：是否分析触发条件、分支谓词、边界值、默认值、异常路径、配置组合。
     3. 状态机深度：是否分析调用顺序、初始化/更新/释放、会话状态、缓存状态、权限状态变化。
     4. 隐式数据流：是否考虑别名、对象字段、全局变量、闭包、回调、序列化/反序列化、日志/缓存/数据库二次传播。
     5. Sanitizer 绕过：是否验证校验函数的真实语义，是否存在编码、大小写、路径规范化、类型转换、双重解析绕过。
     6. 组合漏洞：是否将低危点组合成高危链条，例如信息泄露 + 越权、路径控制 + 符号链接、SSRF + metadata、反序列化 + gadget。
     7. 环境依赖：是否考虑部署配置、权限、容器、K8s RBAC、文件系统、网络拓扑等影响。
   - 输出应是“深挖假设任务卡”：例如“候选路径 P7 在进入 sink 前经过 normalizePath，但未验证 URL decode 后再 join 的双重解析顺序；请构造两阶段编码绕过假设并检查相关代码”。

6. 设计深入性评审 Agent 的量化评分。
   - `evidence_depth`：候选漏洞证据是否包含完整路径、触发条件、消毒绕过、影响证明。
   - `reasoning_depth`：是否解释为什么防护无效，而不是仅指出 source 到 sink。
   - `interprocedural_depth`：跨函数/跨文件/跨对象分析程度。
   - `stateful_depth`：是否分析状态依赖、时序、缓存、权限变化。
   - `bypass_depth`：是否检查 sanitizer/filter 的绕过空间。
   - `chain_depth`：是否寻找漏洞链和组合利用。
   - 深入性评审必须输出：浅层结论清单、需要补证的漏洞、复杂 pattern 假设、深挖优先级、停止深挖的理由。

7. 明确全面性评审和深入性评审的分工与协同。
   - 全面性评审负责“地图上还有哪里没去过”，关注广度、覆盖、漏洞类别和攻击面。
   - 深入性评审负责“已经去过的地方是否挖得足够深”，关注复杂路径、约束、绕过、组合链。
   - 每轮由 Orchestrator 合并两类评审输出，生成下一轮 Worker 任务队列：
     - 70% 预算给最高风险覆盖缺口或深挖假设。
     - 20% 预算给未充分证明的候选漏洞补证。
     - 10% 预算给探索性高不确定方向。
   - 如果全面性和深入性冲突，由风险收益排序决定：`priority = risk_weight * novelty * expected_find_rate * confidence_gap / estimated_cost`。

8. 设计漏洞结果列表的数据结构和误报评审流程。
   - 每个候选漏洞包括：唯一 ID、轮次、状态、漏洞类型、source、sink、完整路径、代码位置、触发条件、攻击者能力、影响、证据、置信度、误报理由、相关任务卡。
   - 结果误报评审只处理新增或被补证的候选漏洞。
   - 状态机：`待结果评审 -> 确认是漏洞 / 确认为误报 / 需要补充证据`。
   - “需要补充证据”应反向生成补证任务卡，由深入性评审参与排序。

9. 设计每轮工作流。
   - 第 0 轮：预处理。
     - 从代码与污点分析文件提取入口、调用图、污点路径、source/sink、风险节点、安全边界。
     - 生成初始 CoverageMatrix 和 DepthMatrix。
   - 第 1 轮：Worker 执行基线审计。
     - 覆盖最高风险 source-sink 路径和最相关漏洞类别。
   - 第 1 轮评审：
     - 误报评审验证新增结果。
     - 全面性评审更新覆盖矩阵并给出未覆盖缺口。
     - 深入性评审检查证据浅深、复杂 pattern 和补证需求。
   - 第 N 轮：
     - Orchestrator 将评审建议编译为任务卡。
     - Worker 执行任务卡，禁止重复已完成任务。
     - 三个评审更新状态。
     - Orchestrator 根据停止条件决定继续或结束。

10. 设计防空转机制。
    - 所有任务卡必须有唯一指纹：范围 + 数据流路径 + 漏洞类别 + 假设。
    - Worker 每轮必须声明哪些任务完成、哪些无法完成以及原因。
    - Orchestrator 拒绝与历史任务相似度过高且没有新证据目标的任务。
    - 对连续无新增发现的方向降权。
    - 对“泛泛建议”要求评审 Agent 重写为可执行任务，否则丢弃。
    - 引入探索预算：每个方向最多重试 K 次，每个漏洞类别最多连续投入 M 轮无收益后暂停。

11. 设计停止控制原则。
    - 最终停止应由程序化 Orchestrator 控制，不应完全交给 LLM。
    - LLM 可以提供停止建议和理由，例如“主要攻击面已覆盖，剩余缺口低风险”，但程序根据硬指标和软指标组合裁决。
    - 原因：LLM 容易过早自信或无限探索；程序化控制可复现、可审计、可配置。

12. 设计停止指标。
    - 硬停止条件：
      1. 达到最大轮次 `max_rounds`。
      2. 达到 token/time/cost 预算。
      3. 所有高风险污点路径达到最低覆盖要求。
      4. 无可执行任务卡。
    - 软停止条件：
      1. 连续 R 轮无新增确认漏洞，且无高价值补证任务。
      2. 新增候选漏洞的确认率持续低于阈值。
      3. 全面性覆盖分数超过阈值，例如高风险路径覆盖 > 90%。
      4. 深入性分数超过阈值，例如高风险候选均完成 sanitizer/状态/组合链检查。
      5. 下一轮任务的期望收益低于成本阈值。
    - 推荐停止公式：
      - 继续条件：存在 `priority >= P_min` 的任务卡，且预算未耗尽，且最近 R 轮仍有足够边际收益。
      - 停止条件：预算触顶，或 `coverage_score >= C_min` 且 `depth_score >= D_min` 且 `marginal_yield < Y_min` 连续 R 轮。

13. 设计任务优先级计算。
    - 对每个候选任务计算：
      - `risk_weight`：sink 危害、攻击面暴露、权限边界。
      - `coverage_gap`：是否覆盖缺口。
      - `depth_gap`：是否存在浅层证据或复杂绕过空间。
      - `novelty`：与历史任务差异。
      - `expected_yield`：相似模式历史产出、路径风险、评审置信度。
      - `cost`：代码范围、路径复杂度、预计 token/时间。
    - `priority = (risk_weight * (coverage_gap + depth_gap) * novelty * expected_yield) / cost`。

14. 设计 Agent 提示词约束。
    - 全面性评审提示词必须禁止输出泛泛安全建议，必须引用具体入口、路径、source、sink、函数、漏洞类别或安全边界。
    - 深入性评审提示词必须要求给出“深挖假设 + 为什么浅层分析可能漏报 + 需要检查的具体条件”。
    - Worker 提示词必须要求按任务卡执行，不得重新发明审计范围；如发现任务外高危问题可作为 side finding 报告。
    - 误报评审提示词必须要求区分“没有证据证明漏洞”和“有证据证明不是漏洞”。

15. 设计输出报告。
    - 最终报告包括：确认漏洞、误报、未完成但高风险方向、覆盖矩阵、深度矩阵、停止理由、资源消耗、剩余风险。
    - 对每个确认漏洞给出完整证据链和修复建议。
    - 对停止时未覆盖的低风险区域明确列出，避免“已完全安全”的错误表述。

## Risks / Open Questions
- 如果污点分析文件本身不完整，全面性评审必须识别“分析盲区”，不能把污点图当作绝对真相。
- 如果代码上下文过大，需要引入分片、摘要和按需检索机制，否则 Agent 容易遗漏或幻觉。
- 如果结果误报评审过严，可能把真实但证据不足的漏洞误判为误报；建议增加“需要补充证据”状态。
- 停止阈值需要按项目风险等级配置：高安全场景应提高覆盖/深度阈值并增加轮次预算。
- 本计划是架构与流程设计，不包含具体代码实现。
